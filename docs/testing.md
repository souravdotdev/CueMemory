# Testing

[Vitest](https://vitest.dev) is wired into every app and package that has runtime logic worth testing, following the same "shared base + per-package config" pattern as ESLint and TypeScript.

## Shared config — `packages/vitest-config`

Two presets, mirroring the eslint-config split between plain Node packages and `apps/web`:

- `./node` (`node.mjs`) — plain Node test environment. Used by `packages/shared`, `packages/db`, `apps/api`, `apps/worker`.
- `./react` (`react.mjs`) — `jsdom` environment + `@vitejs/plugin-react`, built on top of `./node` via `mergeConfig`. Used by `packages/ui`, `apps/web`.

Every package with tests has its own small `vitest.config.ts` importing one of these, and a `test` script (`vitest run`). `apps/api`'s also merges in the `@/` alias (pointing at `src/`) that its `tsconfig.json` declares.

```bash
pnpm test   # vitest run in every package, via Turborepo
```

**Why the shared config files are `.mjs`, not `.ts`** (unlike every other shared config in this repo, which is `.ts`/`.js` extended via a package.json `exports` field): Vite's own config-file loader treats anything resolved through `node_modules` — which is how a pnpm workspace package resolves — as external and leaves it unbundled. A workspace package's raw `.ts` file can't be `import`ed directly by Node (no type-stripping applied), so a `vitest.config.ts` in one package importing a `.ts` file from `@cue-memory/vitest-config` fails with `ERR_UNKNOWN_FILE_EXTENSION`. Plain `.mjs` sidesteps this since Node can load it natively, no transform needed. Each _consuming_ package's own `vitest.config.ts` stays `.ts` — that file is the true entry point Vite bundles directly, so it doesn't hit the same issue.

**jsdom is pinned to `^29.1.1`, not the current `30.x`**: jsdom 30 requires Node `^22.22.2` or newer; this project targets Node `≥20`. jsdom 29 supports `^20.19.0`. If the project's Node baseline moves to 22+, this pin should move too.

## What's actually tested, and why

**`apps/api`** — the flagship test suite, and the direct payoff of the Clean Architecture layering (see [Clean Architecture](./clean-architecture.md)). Tests live in `apps/api/tests/unit/`, in folders that mirror `src/` (`domain/`, `application/`, `infrastructure/`, `interface/`). A use case receives its ports through its constructor, so a test builds it directly with hand-written fakes (`new AdmitSignInUseCase(fakeUserRepository)`, usually `vi.fn()`-based) instead of a container, a real database or Redis. A test that imports a decorated class imports `reflect-metadata` first.

- `domain/rules/signInDecision.test.ts` — `decideSignIn`: an active User → allow, deleted 1 day ago → restore, deleted exactly 30 days ago → restore, deleted 31 days ago (or a moment past the Grace period) → refuse.
- `domain/rules/tagName.test.ts` — `slugifyTagName`'s normalization rules and 50-character limit, and that `TAG_NAME_PATTERN` (which the `tags` CHECK constraint embeds) accepts exactly the slugs it produces.
- `domain/schema-agreement.test.ts` — the Items tables in `@cue-memory/db/schema` agree with the Items domain: the `item_type`, `item_status` and `tag_source` enums hold exactly the domain's Item types, Item statuses and Tag sources, and the Tag name check uses the domain's slug pattern and length limit. `packages/db` can't import the domain, so it keeps literal copies; this test is what stops them drifting.
- `application/use-cases/auth/AdmitSignInUseCase.test.ts` — with a hand-written fake `IUserRepository`: an allowed sign-in refreshes the Display name and avatar, a missing Google name keeps the current one, a restore also clears the deletion time, a refusal throws `UserPermanentlyDeletedError` and changes nothing, a missing Google photo clears the avatar, the email is never in the changes, and a missing User fails with `NotFoundError`.
- `application/use-cases/auth/ResolveSignedInUserUseCase.test.ts` — with a hand-written fake `ISessionProvider`: an active User comes back, and no Session or a deleted User's Session throws `UnauthorizedError`.
- `application/use-cases/auth/GetMeUseCase.test.ts` — the `MeOutput`: display name, avatar and ISO created time, a null avatar URL for a User without one, never the deletion time, and the output parses with `MeResponseSchema`.
- `application/use-cases/items/SaveItemUseCase.test.ts` — over an in-memory `IItemRepository` and a recording `IQueueProvider`: the Source URL is stored for the User as a Processing Item, its Processing is enqueued with the Item's and User's ids, the card comes back Processing with no Item type (and parses with `CreateItemResponseSchema`), the same Source URL saved twice is two Items with two jobs, and an enqueue failure fails the save.
- `application/dto/items/ItemCardOutput.test.ts` — `toItemCardOutput` with a hand-written fake `IThumbnailUrlProvider`: the generic failure message for Failed Items, a null Thumbnail URL for a null Thumbnail key (with or without a provider; an Item with a Thumbnail key and no provider is refused), ISO created time, an empty Tag list for an untagged Item, AI and User Tags (given as domain `AppliedTag` `{ tag, source }` pairs) carrying the right source, no internal fields on the card or its tags, and every output parsing with `ItemCardSchema`.
- `infrastructure/mappers/{itemMapper,tagMapper,userMapper}.test.ts` — `toItem`, `toTag`/`toTagLink` and `toUser`: pure Drizzle-row-to-domain-entity conversion (dates kept as `Date`, the link's denormalized `user_id` dropped, Better Auth's `image` renamed to `profileImg`), with no database connection. The mappers live in their own files so they can be imported without pulling in the Drizzle client (which validates `DATABASE_URL` at module load — see [Environment Variables](./environment-variables.md)). `DrizzleUserRepository` itself isn't unit-tested; its query logic needs a real or containerized Postgres, which isn't set up yet.
- `infrastructure/queue/BullMqQueueProvider.test.ts` — over a recording stand-in for the BullMQ queue's `add`: a Process Item job carries the Item's and User's ids, it's added with 3 attempts, exponential backoff from 5 s and the completed/failed trimming limits, and a payload the worker couldn't read is refused without being added.
- `infrastructure/auth/googleProfile.test.ts` — `googleProfileFromIdToken` on hand-built unsigned JWTs: name and picture claims, a missing photo or name → null, and a non-JWT is refused.
- `infrastructure/auth/signInHook.test.ts` — the session-create hook with a fake Better Auth context and a fake `AdmitSignInUseCase`: the profile comes from the Google Sign-in identity's ID token, a refusal becomes an `APIError` coded `USER_PERMANENTLY_DELETED` with a "permanently deleted" message, any other failure passes through unchanged, and a User without a Google ID token gets an `APIError` coded `GOOGLE_PROFILE_UNAVAILABLE`.
- `infrastructure/auth/BetterAuthSessionProvider.test.ts` — over a fake `getSession`: it passes the request's headers through, no Session is null, and Better Auth's User maps to the domain `User` through `toUser` (avatar to `profileImg`, a missing avatar to null, the deletion time carried over).
- `infrastructure/auth/createAuth.test.ts` builds the real Better Auth instance over `drizzle.mock({ schema })` (no database) and checks only what answers before a table is touched: a provider other than Google gets a 404, a sign-in or link request that adds its own `scopes` gets a 400, Google's authorization URL asks for exactly `openid email profile`, and the Session cookie has no domain unless a cookie domain is configured. Better Auth disables its origin checks under a test runner, so the trusted-origin setting isn't covered here. The full Google round trip can't be automated; it's checked by hand.
- `interface/routes/auth.routes.test.ts` builds the app with a container holding only the environment, the in-memory rate-limit choice and a hand-written fake `AuthRequestHandler`, through `inject`: GET and POST requests reach the handler as web `Request`s with their full URL, headers and raw body (JSON, form-encoded or empty), Better Auth's status, headers, body and every `set-cookie` come back unchanged, and auth routes hit their stricter 30-a-minute limit (the 31st gets `429 rate_limited`) while other routes keep 100.
- `app.test.ts` builds the real app with `buildApp(testContainer())`: a test container with the real use cases and controllers and fakes for Better Auth and the `ISessionProvider` (it binds `RateLimitRedis` to `IN_MEMORY_RATE_LIMITS`, so limits count in memory). It covers `GET /health`, building without a rate-limit store bound being refused, helmet's headers, CORS locked to the web origin with credentials, the app-wide 100-a-minute limit, unknown routes as `404 not_found`, `GET /me` (401 without a Session or for a deleted User, the User in `MeResponseSchema` with internals stripped and a null avatar when there's none), `POST /items` over an in-memory Item repository and a recording queue provider (401 without a Session, 201 with the Processing card, the Item stored for the signed-in User never one named in the body, the Process Item job enqueued, the same URL saved twice as two Items, a generic 500 when enqueueing fails), the auth middleware on a test-only `/protected` route, and the error middleware on test-only routes added after `buildApp`: validation failures as `400 validation_failed` with details, response fields the schema doesn't declare stripped, unmapped client errors and unexpected throws sent with generic messages, and each domain error (`NotFoundError`, `UnauthorizedError`, `UserPermanentlyDeletedError`, `RepositoryError`) sent with its status and a safe message.
- `di/container.test.ts` resolves every `TOKENS` entry through the real `createContainer()`, so removing a binding fails it. It stubs the environment and re-imports after `vi.resetModules()` like `env.test.ts`, and mocks `@/rate-limit-redis` and `@/infrastructure/queue/itemsQueue` (ioredis connects on construction); the Postgres client only connects on its first query, which the test never makes.
- `env.test.ts` checks that the API refuses to start when an auth variable is missing or invalid: it stubs `process.env` with `vi.stubEnv` and re-imports `env.ts` after `vi.resetModules()`, since the module validates once at import time.

**`packages/db`** — `src/entry-points.test.ts` checks that the Postgres client (`@cue-memory/db/client`) and the Redis connection (`@cue-memory/db/redis`) each validate only their own variable: either imports with the other's URL unset, and each refuses to load without a valid URL of its own. Like `env.test.ts` in `apps/api`, it stubs `process.env` and re-imports after `vi.resetModules()`; `ioredis` is mocked so no socket is opened (postgres.js doesn't connect until the first query).

**`packages/shared`** — pure schema tests next to each schema (`schemas/common/error.test.ts`, `schemas/common/pagination.test.ts`, `schemas/auth/me.test.ts`, `schemas/items/create-item.test.ts`, `schemas/items/create-item-response.test.ts`, `schemas/items/item-card.test.ts`, `schemas/items/list-items.test.ts`): what each schema accepts, rejects, defaults and strips.

**`apps/worker`** — tests live in `tests/unit/`, mirroring `src/`, with the same `@/` alias as the API (`vitest.config.ts`). `di/container.test.ts` resolves every `WORKER_TOKENS` entry through the real `createContainer()`, so removing a binding fails it. It stubs `DATABASE_URL`, mocks `@cue-memory/db/redis` (ioredis connects on construction) and re-imports after `vi.resetModules()`, like the API's container test. `domain/rules/itemTypeFromUrl.test.ts` is a table test of the URL rules: at least one URL for every known-site row and every file-extension group, plus profiles, homepages and listings on known hosts that match no row (an X profile, a GitHub organisation, a Spotify artist), `www.`/`m.` hosts, upper-case extensions, query strings and first-match order (a GitHub issue is a Post, not Code); `domain/schema-agreement.test.ts` keeps the worker's Item types and statuses equal to the database enums. `domain/rules/itemTypeFromResponse.test.ts` tables the response rules (Content-Type, `og:type` in its attribute spellings). `application/use-cases/items/ProcessItemUseCase.test.ts` runs the use case over an in-memory Item repository and a fake `IUrlFetcher`: a URL rule skips the fetch, an unmatched URL is typed by the response, a fetch error propagates. `infrastructure/http/publicAddress.test.ts` tables allowed and refused addresses; `infrastructure/http/SafeUrlFetcher.test.ts` runs the fetcher against a local `node:http` server on 127.0.0.1 (redirects, the 5-redirect cap, the size cap, timeouts, User-Agent) with a test resolver for `.test` names and an address check widened to allow 127.0.0.1 only, plus refusals through the real guard (each blocked range, never connecting) and redirects into the network. `interface/itemsWorker.test.ts` is the processor seam: it drives `runItemsJob` with fake jobs and a test container whose use case is a stand-in, checking that an unknown job name or an invalid payload throws `UnrecoverableError` (no retry) and that a Processing error passes through (retried). `application/use-cases/items/FailItemUseCase.test.ts` checks that a Failed Item with no Item type becomes a Link and one with a type keeps it, and that a missing or other User's Item is untouched. `interface/itemsJobFailed.test.ts` drives `onItemsJobFailed` with fake jobs and a stand-in `FailItemUseCase`: a job BullMQ has finished with (it set `finishedOn`: the last retry, or a job that stalled too often) marks the Item whatever its attempt count, a job BullMQ will retry doesn't, an invalid payload or an unknown name changes no Item, every failure reason is logged, and a marking error is logged rather than thrown.

**`apps/web`** — `save-form.test.tsx` tests the `SaveForm` client component with `@testing-library/react` + `@testing-library/user-event`, mocking `next/navigation`'s `useRouter` and the `@/lib/api` module (so no real `fetch` call or `NEXT_PUBLIC_API_URL` env var is needed). `src/lib/api.test.ts` tests the API helpers themselves against a stubbed global `fetch` (`vi.stubGlobal`): a valid response returns the parsed shape, a response that breaks its schema throws, and a failure throws the error envelope's `message`.

**`packages/ui`** — `button.test.tsx` — a basic render/click/disabled-state test proving the `jsdom` + React preset works, independent of any app.

## Fakes over mocking libraries

Every fake used across these tests is either a small hand-written object literal or a `vi.fn()` — no separate mocking framework, and no shared "fakes" package. Given how small each port interface is (1-3 methods), writing the fake inline in the test file that needs it is less overhead than maintaining a shared fixture module, and keeps each test file readable on its own.

## Pre-push gate

`.husky/pre-push` runs `pnpm lint && pnpm check-types && pnpm test` — tests are part of the last gate before code leaves the machine, alongside lint and type-checking (see [Code Quality](./code-quality.md)). They're not part of `pre-commit` (`lint-staged`), since running a full test suite on every commit — including ones that don't touch tested code — would slow down the fast, scoped pre-commit check down considerably.

## A real bug this setup caught while being built

Building the `apps/api` route tests originally surfaced a genuine regression risk: `tsc` (then `apps/api`'s/`apps/worker`'s build tool) compiled `*.test.ts` files into `dist/` alongside real source, and Vitest's default file-discovery glob picked up both the source test and its compiled `dist/` copy — silently double-running every test, and shipping test files in what's meant to be production build output. Originally fixed by excluding `**/*.test.ts`/`**/*.test.tsx` in those apps' `tsconfig.json`. That exclusion was later removed once `apps/api`/`apps/worker` switched their production build to `tsup` (see [Architecture](./architecture.md#monorepo-layout)) — a bundler only pulls in files actually reachable from its entry point, so test files never leak into `dist/` regardless of tsconfig excludes, and removing the exclusion restored `tsc --noEmit`'s type-checking coverage for test files, which it had been silently skipping. The `**/dist/**` exclude in the shared Vitest config stays in place regardless, as a second line of defense.
